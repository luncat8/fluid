# 0.1.1 — cpu reference solver, conformance suite, experiments harness

status: planned
depends on: 0.0.0 (section 5 is the spec it implements)
parallel with: 0.1.0
milestone: infrastructure

## 1. goal

an independent, compact implementation of the 0.0.0 section 5 scheme on typed arrays
that runs in node without a gpu, plus the experiment scripts that turn every later
plan's acceptance criteria into numbers in experiments/logs. the cpu solver is the
numeric oracle: it decides whether a scheme is conservative, monotone and stable
before any wgsl is written, and it is the reference side of gpu parity tests.

## 2. scope

in: src/core/solver.js implementing passes 1..13 of 0.0.0 section 8 in cpu form,
src/core/eos.js, src/core/stats.js, the experiment runner scripts, the conformance
suite, log format.

out: gpu code (0.1.0), fct limiting (implemented here first as the reference, then
ported in 0.3.1), multigrid (0.6.0).

## 3. why the duplication is acceptable

the wgsl and the cpu solver implement the same scheme twice. that is deliberate:
	- the scheme is written once, in prose with formulas, in 0.0.0 section 5.
	- both implementations are checked against the same conformance suite, so a
	  divergence shows up as a failing number rather than a mystery on screen.
	- the cpu version stays small (one file, no pools, no bind groups, no ping pong
	  objects: two typed arrays per field and an index swap) and is readable in one
	  sitting, which the gpu version cannot be.
the cpu version is not a mirror of the gpu version and must not grow gpu concepts.
if a formula is unclear, fix 0.0.0 section 5, then both.

## 4. design

### 4.1 layout

same (N+2)x(N+2) ghost ring, same index math (src/core/grid.js is shared, required
by node directly). fields as Float32Array, flags as Uint8Array. two buffers per
ping pong field, swapped by exchanging references (no copies).

all kernels are flat loops with early continue, no nesting beyond two levels, and no
allocation inside a step: scratch arrays are allocated once in create().

### 4.2 api

	Fluid.core.solver.create(cfg)      -> sim object with fields, cfg, ledger
	sim.reset(scenario)                -> scenario = compact string map + emitter list
	sim.step(dt)                       -> one full pass graph, substepping inside
	sim.stats()                        -> totals, mins, residuals, drift (no allocation:
	                                     writes into a preallocated result object)
	sim.field(name)                    -> typed array for inspection
	sim.dumpCsv(name, path)            -> for gpu parity comparison
	sim.assertInvariants(tol)          -> throws with a precise message on violation

### 4.3 invariants checked every step in debug mode

	i1 sum(m), sum(dr), sum(dg), sum(db) unchanged within tol of the ledger expectation
	i2 sum(E) unchanged within tol (with conduction and exchange on: still unchanged,
	   they are pairwise conservative; with heaters on: equal to the injected amount)
	i3 min(m) >= 0, min(dr/dg/db) >= 0, min(E) >= 0
	i4 max(T) and min(T) within the physical range implied by the eos, no NaN, no Inf
	i5 |div(u)| max residual after projection below the configured threshold
	i6 phi_l, phi_g inside [0,1], phase byte consistent with them
	i7 no cell has m > 0 and phase = vacuum, and no cell has m < m_eps and phase != vacuum

any violation prints the step number, the invariant, the offending cell index and the
values around it. this is the debug output that makes the gpu port fast.

### 4.4 experiments

all scripts: node experiments/<name>.js [--N=64] [--steps=1000] [--log], print a
compact table to stdout and append to experiments/logs/<date>-<name>.log. no
dependencies, no npm install, deterministic (fixed seeds, fixed dt).

| script | what it measures | used by |
|---|---|---|
| conservation.js | drift of every invariant over N steps, closed box, stirring on, with and without fct, with float32 vs a simulated float16 rounding pass | 0.3.0, 0.3.1 |
| sharpness.js | color interface width over time (gradient magnitude integral of a dye edge), upwind vs fct | 0.3.0, 0.3.1 |
| monotone.js | min/max of dye and m over time, extremum count, negative cell count | 0.3.1 |
| stability.js | cfl sweep: max velocity, dt, substeps -> blow up point; viscosity and conductivity sweeps | 0.2.0, 0.4.0 |
| convection.js | bottom heated box: time to plume onset, max vertical velocity, roll count, Nusselt style heat transport ratio, energy budget closure | 0.4.0 |
| phase.js | heat a solid block: time series of phase fractions, T plateau at T_melt and T_boil, energy budget including latent heat, volume expansion of the produced gas | 0.5.0 |
| eos.js | unit checks of the caloric eos: monotone T(E), plateau boundaries, rho* continuity, S sign and clamp | 0.5.0 |
| projection.js | poisson residual vs jacobi iterations at several density ratios; cost estimate; whether K=40 is enough at 512^2 | 0.2.0, 0.6.0 |
| lbm-probe.js | deferred, see 0.9.0 | 0.9.0 |

log format: header line with date, script, git rev, config as key=value, then the
table, then a verdict line (pass/fail against the thresholds in the plan). logs are
kept in git (small text), never regenerated silently.

### 4.5 conformance suite

experiments/conformance.js runs a fixed list of scenarios (small closed box, dye
blob, heated bottom, melting block) and asserts the invariants plus per scenario
expected outcomes. it is the same list the gpu parity test uses, so a single table
describes both sides:

	scenario name, N, dt, steps, initial state string, expected invariant tolerances,
	expected qualitative outcome (e.g. "plume reaches y > 0.6N before step 800")

## 7. acceptance

- a1 node experiments/conformance.js exits 0 with all scenarios passing on N=64.
- a2 conservation.js: relative drift of m and each dye below 1e-6 after 1000 steps
	with stirring and emitters active, and exactly 0 with them off (closed box, no
	sources). energy drift below 1e-6 with conduction on.
- a3 monotone.js: zero negative cells, zero new extrema beyond the fct bound, over
	1000 steps.
- a4 sharpness.js produces the upwind vs fct interface width curves that justify the
	0.3.1 decision (numbers recorded in the log).
- a5 stability.js finds the cfl limit and reports the substep rule used by 0.2.0.
- a6 convection.js: bottom heated box reaches a steady plume/roll state, energy
	budget closure below 0.1 %, onset time recorded. this number is the target for
	milestone 2 on the gpu.
- a7 phase.js: T plateaus at T_melt and T_boil are visible in the time series, the
	latent heat charged equals m*L within 0.1 %, gas volume expands by the expected
	rho_liq/rho_gas factor within 5 %. this is the target for milestone 3.
- a8 total runtime of the whole suite under 30 s on the dev machine at N=64.

## 8. risks and pitfalls

- the cpu solver drifting from the wgsl over time: the conformance scenario table is
	the shared contract, and any scheme change must edit 0.0.0 section 5 first.
- float32 typed arrays in js are exact ieee single precision, so cpu numbers are
	directly comparable to gpu f32; but the summation order differs (cpu linear, gpu
	hierarchical), so parity tolerances must allow for that (~1e-6 relative).
- ghost ring handling is the most common source of "mass leaks at the border": test
	a full box at exactly rho_liq with zero velocity and assert the border cells never
	change.
- jacobi on the cpu at N=64 converges fast enough to look fine and hide a bad
	iteration count for N=512; projection.js must sweep N as well as K.
- node has no requestAnimationFrame: experiment loops are plain for loops with a
	progress print every 100 steps.

## 9. next

solver after each port. the parity test is the fastest way to find a layout bug.
