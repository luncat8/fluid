## review of the previous task

The a10 sign-off (docs only) named the cost structure to attack: ~2.1-2.6 ms per
substep at 512^2, frame rate bound by the auto-substep count in boiling
scenarios, `jet` the watch case. Counting dispatches in the shipping
configuration (MG 2 cycles, pre4/post8, K=60) sharpens that: one projection is
295 dispatches, of which 240 are coarse-level (129^2) red/black sweeps — the
projection is plausibly dispatch-bound rather than cell-bound, but only
per-group GPU timestamps on the target hardware can say. The 0.6.0 plan
predated that context (it still called red-black the baseline and MG unbuilt);
its premises are updated below.

## changes

- `src/gpu/profiler.js` (new): guarded timestamp-query profiler. Times five
  groups per substep (`vel`, `rhs`, `press`, `trans`, `phase`) plus `stats`,
  `disp`, `render` per frame; 128 query pairs cover 24 substeps; results are
  summed per group through a 2-slot MAP_READ ring with the same generation
  guard as stats/buoy. `create()` returns null without the feature — the sim
  never depends on it. Contract suite: `experiments/profiler.js` (wired into
  run-all quick + full).
- `src/gpu/passes.js`: `encodeStep` split into five segment encoders threaded
  by a reused io object; `encodeStepProfiled` replays the identical dispatch
  sequence with a pass split at each segment. The non-profiled path is
  byte-equivalent in behavior (verified mechanically, see validation).
- `src/gpu/solver.js`: `frame()` branches on `cfg.gpuTiming` (profiled vs the
  single-pass fast path), render pass takes timestampWrites while profiling,
  `pollReadback()` also polls the profiler, new `getProfile()`; profiler is
  invalidated on reset and destroyed with the solver. Unaffected by resize
  (capacity is N-independent).
- `src/gpu/device.js`: requests `timestamp-query` only when the adapter
  offers it; returns a `timestamps` flag.
- `src/core/config.js`: `gpuTiming: 0` default (JS-side only).
- `index.html` + `src/app/controls.js` + `src/app/hud.js`: "GPU times"
  checkbox; HUD perf block and the copyable snapshot gain a per-group
  ms/substep line while enabled ("unavailable (no timestamp-query)" when the
  adapter lacks the feature).
- `experiments/browser-tests.html`: `&profile=1` adds an adapter-capability
  header line and a per-scenario `gpu timing` line (ms/substep per group +
  step sum + disp/render/stats per frame); `&k=` added next to the existing
  `&cycles=&pre=&post=&s=` solver sweep params. Profile stays off by default
  so sign-off captures remain comparable.
- `experiments/gpu-parity.mjs`: loads profiler.js (returns null on backends
  without the feature).
- `experiments/mg-work.js`, `experiments/mg-work2.js` (new): CPU-oracle
  solver-work studies (below).
- `0.6.0-plan.md`: status, section 3 (recorded baseline), timing/benchmarks,
  section 4.1 (MG is the baseline; measured variant verdicts) and task marks
  (t1, t3, t4 done; t2 reworded to the query-param harness).

## solver-work findings (CPU oracle, dt=1/240, warm-started)

Round 1 (`mg-work.js`, div-based):

- `divAfter` is useless for judging the solve in boiling scenarios — it
  floors at max|S| (~19/s in jet) for every variant from RB K20 to the full
  default. True residual (`residualNorm()/divBefore`, round 2) or dam (S=0)
  discriminate.
- dam: default relRes 4.6e-4 vs 9.2e-3 at 1 cycle — the second V-cycle buys
  ~20x. RB K60 (3.8e-2, 60 feq) loses to MG 1-cycle K20 (9.0e-3, 16.3 feq):
  MG default validated once more.
- pre2/post4 at 1 cycle **blows up** in cycle (NaN fields; round 2 bisects it
  to step 40). Rejected candidate, recorded per a6.

Round 2 (`mg-work2.js`, true residual + K sweep + stability):

- dam K sweep at 2 cycles: div med 0.167 (K60) -> 0.293 (K20) -> 0.554 (K12)
  -> 1.06 (K8); max-norm trueRes pinned ~7.7e-2 by stiff interface cells.
  K20 is the sweet spot: 295 -> 135 dispatches per projection for a div that
  stays ≪ 1.
- jet/cycle: trueRes identical for default, c2K20 and c1K20 (3.3e-2 / 4.0e-2).
  In the ns-expensive boiling scenarios the cheap variant is measurably as
  good per substep at 45 % of the work and 23 % of the dispatches.
- stability: only the minimal corner 1-cycle pre2/post4 is unstable;
  pre2/post8, pre3/post6 and 2-cycle pre2/post4 all survive 480 steps. The
  shipping default sits far from the edge.

No defaults were changed (t11): the plan's a6 requires a hardware before/after
row per adoption, and the value of the K/cycles cuts depends on Ampere
dispatch overhead, which this environment cannot measure (no Vulkan ICD).

## validation

- `node experiments/run-all.js --quick`: all 11 suites pass, including the
  new `profiler.js` contract (aggregation over substeps, render tsWrites
  indices, ring reuse, generation guard dropping stale samples, 128-pair
  capacity clamp, null without the feature), the real-encoder `gpu-mock.js`,
  and the fake-device browser harness (stub solver has no `getProfile` — the
  page calls it defensively).
- Encode refactor equivalence: the ordered setPipeline/setBindGroup/dispatch
  sequence of the new `passes.js` was diffed against `git show HEAD` — 113
  ops, identical modulo one `wx,wy` spelling. Profiled frames therefore run
  the same kernels in the same order; parity cannot drift between modes.
- `node --check` on every touched file; browser-tests inline script likewise.
- GPU execution (Dawn parity, timestamp path on a real adapter) is not
  available in this sandbox and remains for the user's device, as with prior
  milestones. The profiler degrades to null on any adapter without the
  feature, so the risk surface is the profiled encode branch only.
