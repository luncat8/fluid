## what is already known

- The failing cells are **always on the `y=1` edge row** (`20,64`, `47,6`, `27,1`, `29,1`, `40,2`,
  `30,2`, `31,1`, `19,1`, `25,1`). Never interior. The ghost ring is 0 there and `isBlocked`
  treats `y<1` as wall, so the edge is the one place a clamp reads zero pressure.
- **Mass swings thousands of times between substeps** on the cells involved:
  `0.70 → 20.5 → 6.7 → 8.7`, and `59.3 → 12.2 → 0.01`. That is the input to the `1/ρ` face weight
  (`1/(2·ra·rb/(ra+rb))`, floored at `rhoVac=1e-3`).
- **The solve residual is 5-6 orders above the rhs** while the field is still finite:
  `poissonRes 6.91e11` vs `poissonRhs 8.74e5`; then `1.39e29` vs `2.38e6`. The solve is
  diverging, not merely inaccurate.
- **Pressure amplifies ~10x per substep, every substep** once it starts:
  `-1.5e16 → -8.8e17 → 9.9e18 → 2.0e20 → -1.7e22 → -6.1e24 → -3.4e27 → -2.0e30`.
  Velocity is already pinned at the clamp (`378`, `480`) throughout, so pressure runs away first.

## leads, in the order the evidence supports

1. **Solve convergence under the runaway.** The fixed ~10x-per-substep gain looks like an
   iteration-gain problem in `project` / the v-cycle, not a source problem. Ask whether the
   Gauss-Seidel / multigrid sweep is stable when face weights span many decades, and whether
   `mgPre=4 / mgPost=8 / mgCycles=2` are adequate at `ns=24` with `solverIters=20`.
2. **The edge row.** Why does the runaway always start at `y=1`? Follow the ghost-ring zero and
   the `x<=1 || isBlocked(...)` guards in `applyGrad`, `imprintColliders` and `faceW`.
3. **Where the mass swing comes from.** `59.3 → 0.01` in one substep on an *open* cell is not
   physical. If that is itself a bug, the pressure story is downstream of it.

## rejected — measured, do not re-ship as a fix

| change | result |
|---|---|
| `applyGrad` clamp to `vClamp` (cpu + wgsl) | dies 219 instead of 218 — one substep later |
| global pressure gauge after `project` | dies 248 |
| per-component (flood-fill) gauge | dies 78 (no isolated pocket; hypothesis dead) |
| divergence masked by the operator's own face mask in `poissonRhs` | dies 16-30, **worse** |
| rhs mean subtraction (compatibility projection) | dies 248 |
| density floor 0.02 / 0.08 / 0.3 / 0.5 on `faceW`+`faceInvRho`+mg | dies 21/20/20/22, **worse** |

The density-floor result matters: it makes things four times worse, so the simple reading of the
`1/ρ` story ("the floor is too low") is wrong. Also note the `applyGrad` clamp is arguably correct
on its own — it is the only unbounded velocity write in the solver — but it is not the fix, and
shipping it as one would repeat the 0.7.2 mistake.

## two traps

- **Do not gate on `poissonRes` / `divBefore` / `rhsSum` after the field is dead.** They read 0 or
  stale when `captureSolveResidual` runs on a non-finite field. Test while finite.
- **Instrumented runs only reproduce if the pass list matches `step()` exactly**, including
  `updateColliderMask()` and `imprintColliders()`. Omitting either changes the physics.
