date: 2026-10-25
plan: 0.7.0-plan.md t12 + acceptance a6

## review of the previous task

The previous stage closed `0.7.0` `t6` (binary snapshot), `t9` (batched `onPhaseChange`)
and `t12` (device lifecycle + replay). The code was validated by the CPU suites, the
recording mock and the WGSL interpreter, so the numeric and plumbing claims hold. What
neither the mock nor the interpreter can see is a page's *script graph*: an HTML runner
with a renamed or missing module loads fine, fails silently, and only surfaces when the
page is opened on a device.

That is not hypothetical. `experiments/api-test.html` still referenced
`../src/app/loop.js` (removed when the frame loop became `Fluid.engine.update()`) and did
not load `src/core/pacing.js`. `Fluid.engine.create` calls
`Fluid.core.pacing.create(...)`, so the t12 page - the only browser-side lifecycle,
leak and replay check - threw on its first call and showed nothing. `engine.js` could not
notice because it requires the modules directly in node order, and `api-test.js` itself
was covered headlessly.

The second gap was acceptance `a6` ("no allocation in `update()/step()/render()`"),
marked done in the plan text but never measured.

## implementation

- `experiments/pages.js` (new suite): discovers every `*.html` runner and checks, per page,
  that each `<script src>` resolves; that every `Fluid.*` namespace used by a loaded script
  or the page's inline script is defined by another loaded script (naming the defining
  module on failure); that loading the scripts in document order in a stub browser does not
  throw; and that the entry points the inline script calls exist afterwards. It checks
  where a namespace comes from, not the order of every reference: classic scripts defer
  their bodies, so a definer may legitimately load after the file that uses it inside a
  function.
- the same suite drives the `api-test.html` page itself: its inline `run()` is executed
  against a canned `runLifecycleSuite` result with a stub element registry, once for a
  passing result and once for a failing one. That covers the page's own reporting path -
  status/class, summary totals, both tables, the failure label - without paying for 20
  device cycles, which `engine.js` already runs with the real suite.
- `experiments/api-test.html`: dropped `src/app/loop.js`, added `src/core/pacing.js` in
  the same position `examples/demo.html` uses. The page now boots.
- `experiments/engine.js`: new `a6` section. The array constructors are wrapped for the
  duration of the audit, each allocation is attributed to its innermost caller, and only
  the synchronous `update()`/`render()`/`stats()`/`sample()` window is counted (async
  readback continuations land outside it, and the mock device allocates in its own file, so
  harness churn is excluded). 200 engine frames plus 100 CPU reference steps allocate `0`
  typed arrays or ArrayBuffers inside `src/`. Three positive controls keep the check honest:
  the same window must advance the simulation by exactly the scheduled frame count, the
  harness allocations must still be visible (`1260` over 200 frames), and the audit itself
  makes one allocation inside the window when nothing else fires, so a dead constructor
  wrapper cannot pass by counting nothing. `subarray`/`slice`/`{}` do not run a constructor and are
  not covered - the claim is about the large typed-array allocations.
- `experiments/run-all.js`: `pages.js` added to both profiles (13 suites).
- `README.md`: `pages.js` in the validation list, the `a6` audit in the `engine.js` line,
  the quick-profile duration, and a note that `api-test.js` runs headlessly as well as in
  the browser. `0.7.0-plan.md`: `a6` closed with its evidence, `t12` records the page and
  allocation guards.

## validation

- `node experiments/pages.js`: all 19 page checks pass over the 4 runners, `0.05 s`.
  Reverting the `api-test.html` fix reproduces both failures (`missing ../src/app/loop.js`
  and `core.pacing needs src/core/pacing.js (used by src/api/engine.js)`), so the check
  detects the bug it was written for; renaming one `res.totals` key in the page's summary
  text makes the page-flow check fail, so the reporting path is covered too.
- one-off end-to-end run: the repaired page's scripts, inline `run()` and the real 20-cycle
  suite were executed in node against the recording mock device (`status=PASS`, `8/8`
  checks, 8 check rows, 20 cycle rows, `~17 s`). That is the same code the browser runs,
  minus the driver.
- `node experiments/engine.js`: all 110 checks pass, including the four new `a6` checks
  (`frames=210`, `seen=1260`, `0` engine allocations in `src/`, `105` cpu steps with `0`
  allocations in `src/`).
- `node experiments/run-all.js --quick`: **PASS all 13 suites · ~10 s** (was 7.4 s across 12).
- `git diff --check` passes. No real-device pass was available in this stage; the page fix
  is verified by loading the page's scripts in node, not by a browser. The longer numerical
  histories were not rerun: only harness, page and documentation files changed, no solver,
  WGSL or save-format code.
