date: 2026-10-25
status: implemented, validated headlessly (mock device + allocation audit); device timing row open
plan: 0.7.2-plan.md
source: the "next step" of archive/0.7.1-page-wiring-worklog.md ("the last per-frame allocation

## review of the previous task (0.7.1)

0.7.1 (page wiring + the `a6` allocation audit) is sound, and its suggestion was the right
place to look. its *proposed fix* was wrong, though, and that is the main finding here:

- it proposed "reusing a persisted view per readback buffer". `getMappedRange()` returns an
  `ArrayBuffer` that `unmap()` **detaches**; a view kept across frames is dead on the next
  map and throws on read. it would also have passed the headless suites, because
  `experiments/mock-device.js` returned its backing `ArrayBuffer` directly from
  `getMappedRange()` and never detached anything. a mock that is kinder than the spec is a
  test that cannot fail - so the mock is now faithful: a snapshot per `mapAsync`, one
  `ArrayBuffer` per (offset,size) per map, detached on `unmap` via `structuredClone(transfer)`.
- the real cost was never the view (one per map is the floor) but the *number of maps*:
  four channels, four `MAP_READ` buffers, four poll loops, up to four map/unmap round trips
  per frame. measured on the mock: 3 maps and 3 typed-array views per step+poll cycle with
  stats, buoy and probes all due.
- `readbackArray.set(new Float32Array(getMappedRange()))` in the stats poll copied 46 floats
  through a second array every frame for no benefit; the slot is now read straight out of
  the mapped view with an explicit float copy.

## implementation

- `src/gpu/fields.js`: `readbackLayout()` + `READ_CHANNELS` + `SLOT_ALIGN` (256). the four
  `*Read` buffers (`statsRead`, `buoyRead`, `probesRead`, `phaseEventsRead`) are replaced by
  one `pool.readback` (`MAP_READ|COPY_DST`, 5120 B) plus `pool.readSlots` / `pool.readBytes`.
  the pool's buffer list (destroy + the memory audit walk it) is updated in the same place,
  so nothing is destroyed-but-uncounted.
- `src/gpu/solver.js`: `readMask` (one bit per channel) replaces `pendingRead`, `buoyPending`,
  `probePending`, `phasePending`; `readInFlight` replaces `readbackInFlight`, `buoyInFlight`,
  `probeInFlight`, `phaseInFlight`. `pollStats`/`pollBuoy`/`pollProbe`/`pollPhaseEvents` and
  their four copies become `pollMap()` plus `ingestStats(view, frame)`; buoy, probe and phase
  ingestion are three-line blocks reading their slot. `mappedFloats()` caches the view by
  `ArrayBuffer` identity (one view per map, never a detached one); `copyFloats()` is the
  allocation-free slot copy. `resize()` refreshes the slot table and drops the cached view.
- `needPhase` no longer depends on in-flight state: the pass always runs while a listener is
  registered, and only the *copy* is skipped while a map is open. a skipped copy is not a
  lost sample - the storage buffer holds the newest values for the next copy - which is why
  one shared flag can replace four.
- unchanged on purpose: channel cadences, the generation guard, the stats expected-totals
  capture at encode time, and the phase callback firing outside the map.

`python3 run_tests.py` - **PASS all 13 suites, 8.4 s**
(`experiments/logs/2026-10-25-16-54-test-suite.log`).
`python3 run_tests.py --full` - **PASS all 21 suites, 1290.9 s**
(`experiments/logs/2026-10-25-16-55-test-suite.log`): the long numerical histories are
unchanged, as expected - no kernel, ingest rule or conservation formula was touched.

new checks:

- `experiments/gpu-mock.js` gained section 10 (`testReadbackStaging`), 7 checks: one
  `MAP_READ` buffer in the pool and no per-channel twins; four slots 256-aligned, ordered,
  disjoint, summing to the buffer size; a frame owing every channel (stats + buoy + probe +
  phase listener) encodes 4 copies at the 4 slot offsets and takes 1 map; a frame submitted
  while that map is open copies nothing and maps nothing; the next frame catches up with 4
  copies and 1 map; `getMappedRange` hands out a fresh `ArrayBuffer` per map that `unmap`
  detaches (`5120 B -> 0 B`); teardown leaks nothing. the existing buoy/probe/phase readback
  checks were retargeted from the removed read twins to `readback` + slot offset (the mock's
  copy record now carries source and destination offsets).
- `experiments/engine.js` gained `testReadbackAllocations` (2 checks, 112 total): a whole
  `step()` + `pollReadback()` cycle costs exactly one typed array in `src/` per map -
  `40 allocations in src/ for 40 maps (40x Float32Array @ src/gpu/solver.js)` - and never a
  stray second one. the probe was factored out of `a6` into `createAllocProbe()` so the
  synchronous audit (window per frame) and the asynchronous one (window across the await)
  share one implementation.

before/after, same 40 step+poll cycles, N=64 dam with stats + buoy + probe due every frame
(measured against the HEAD tree in a temporary worktree):

	before   3 maps per cycle, 120 maps, 120 typed-array views in src/
	after    1 map  per cycle,  40 maps,  40 typed-array views in src/

that is the whole claim: three driver round trips per frame become one, the allocation floor
is reached (one view per map, from the driver's own per-map `ArrayBuffer`), and the four
poll loops collapse into one.

correctness rests on the existing suites rather than on new numerics: the mock runs no
shader, and the readback change moves bytes between buffers without touching a kernel, an
ingest rule or a conservation formula. the phase-event, probe and buoy readback checks all
still deliver the same values (`sub=0.5`, `m=1 db=0.6 u=7 p=44`, `total=2 melt=1 boil=1`).

## decisions and caveats

- device timing is not measured here: the window is the number of `mapAsync` round trips,
  which needs a real driver to price. `queue ms` in the HUD is the first place a win or a
  regression would show. this is the open row for 0.7.2.
- one map per frame means the four channels now share a single in-flight gate. a channel
  whose copy is skipped waits one frame; `probeEvery`/`buoySampleEvery` are therefore "at
  most every N frames" rather than exactly. the staleness contract (`sample.age`, the stats
  frame number) already told callers this.
- `mapAsync` of the whole 5120 B staging buffer is not free but is not per-channel either;
  mapping a sub-range would not save a round trip and would add alignment cases.
- the save/load staging buffer and the GPU profiler's resolve buffers stay separate: one is a
  one-shot texture capture, the other is opt-in and copies many small ranges. folding them
  in would make a save wait for a frame's readback.
