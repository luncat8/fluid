## what the ladder says

1. **the cost law.** press = 0.026 + cycles * (0.466 + 0.0071*K) ms/substep fits all four
   rows (K40 predicted 1.526 vs measured 1.509, +1.2 %). One coarse sweep is 7.1 us and the part
   of a V-cycle that is *not* the coarse solve — 12 fine sweeps plus coarsen/restrict/
   prolong — is 466 us. Consequences: 60 -> 20 removes 31 % of press and 20 -> 0 would
   remove only 23 % more, so K is a spent lever; halving the cycle count removes 49 % of
   press, and a third level, which shrinks both terms, is the only thing left in this
   kernel. The non-press half of a substep is 0.27-0.32 ms and does not move with K or with the cycle count.
2. **the a2 trade has a price now.** K=40 costs +0.28 ms/substep = 17 % of the fps at
   N=512 (104 -> 87) and 17-19 % in the auto policy — not the "~12 fps" carried over
   from the auto rows in t11. K=20 stays the default (its controlled true residual at
   N=512 is *lower* than the reference's, -0.04 %, and +8 % peak divergence at the same
   state), and `&k=40` remains the a2-conservative fallback, now with a measured row so
   the switch is a config decision rather than a guess.
3. **1 cycle: the hardware agrees with the oracle, in a way the old report could not
   show.** +53 % fps on cycle and +56 % on jet, but blobs' sampled maxDiv goes
   2.81 -> 6.27, dam and cycle gain 19980/27577 sampled overpacked cells, and dam
   still ends frame 600 with 1191 overpacked cells where all three 2-cycle rows end with
   0. Rejected as a default, unchanged verdict; the scenario-conditional option stays
   open and now has a metric to be judged by (below).
4. **the sampled maxDiv column cannot rank the solver, and the direction is all it
   gives.** across the fixed rows it rises monotonically with fewer sweeps (blobs
   1.06/1.51/2.81/6.27 for K60/K40/K20/K20-c1), which matches the oracle's ordering, but
   the same column in `cycle` reads 31.7/31.2/30.3 (flat, S-floored) and then 122 for
   1 cycle, and in `jet` it *falls* from 25.2 to 22.3. A hardware A/B that reads
   divergence peaks is reading the splash, not the projection.

## the fix this task needed: the true residual in the hardware stats

Item 4 is why the last open step of t11 is in this commit. `max|b - L p|` and `max|b|`
are now two more channels of the existing stats reduction, so every hardware report can
be ranked by the number plan 4.1 designates as the judge, at any scenario, with no
oracle in the loop.

- `src/gpu/shaders.js`: the poisson operator (open-cell test, harmonic-mean face
  weights, `b - (sum - wsum*p)`) moved out of `mgRestrict` into `POISSON_HELPERS` and
  interpolated into both that kernel and `statsReduceA`; only the five pressure reads
  stay in each caller, because the solver holds press as a storage texture and the stats
  pass as a sampled one. `statsReduceA` now reduces 35 slots (was 33) and
  `statsReduceB` writes slots 32/33.
- `src/core/stats.js`: `IDX_POISSON_RES=32`, `IDX_POISSON_RHS=33`, `STATS_LEN=32 -> 36`.
  `src/gpu/fields.js` sizes both stats buffers and the partial stride from that layout
  instead of repeating 128 and 40, and `src/gpu/solver.js` reads the slots into
  `diag.poissonRes/poissonRhs/poissonRel` and copies `STATS_LEN*4` bytes.
- `src/core/solver.js`: the CPU path fills the same two diag fields from the same state
  (the post-phase fields at the end of the last substep) by calling
  `multigrid.computeResidual` with `out=null`; it is recomputed per `stats()` call, while
  the gpu value is the last sampled frame's readback. To make that a single definition rather than a copy, `faceW` and
  `computeResidual` moved to module scope in `src/core/multigrid.js` and the v-cycle now
  calls them; the max is folded into the residual loop, so `residualNorm()` is that same
  call and no scratch array is added.
- reporting: `poisson: res= rhs= true=` after the maxM line in the browser report and in
  the `s`-key HUD snapshot, `poissonTrue=` in the sampled-peaks line (the max over
  sampled frames), and `| poisson residual <ratio>` in the health line.
- cost: one extra texture read per cell in a pass that runs every 30 frames; that pass
  reads 0.24-0.32 ms per sampled frame today and the buffers grow by 16 B. Whether the
  extra read moves either number is a question for the next capture, not a claim here.
  The cpu side is measurable now: at N=512 `stats()` goes 6.1 -> 16.7 ms per call
  (the operator is ~a dozen loads per cell), i.e. 2 % of the 858 ms cpu substep, and it
  only runs when something asks for stats — the polling exception is experiments/phase.js
  (600 calls at N=64, ~+1.7 % on that suite). The channel is reporting only — no gate reads it, so a wrong
  number there cannot change the simulation.
- semantics: this is the residual of the *last substep's* solve, evaluated with the
  post-phase mass and flags. That is exactly when the oracle reads it, so the numbers
  are the same quantity, and it is also why it is a consistent bias rather than a
  per-candidate one: the coefficient drift has nothing to do with K or the cycle count.

## decisions

- DEFAULT UNCHANGED: `mgCoarseIters: 20`, 2 cycles. K=40 is recorded with its price
  (17 % of fps for 8.8e-4 vs 1.9e-3 on the trajectory rows, both readings below the
  reference's own N=512 splash number). If a2 is to be read as a hard bar at N=256+
  rather than a settled-state target, this one line flips and the cost is now known.
- t2 CLOSED for N=512 (both policies) and N=1024 (auto). The N=1024 fixed-policy row is
  the one measurement still missing; it is listed in section 3 rather than pretended.
- the scenario-conditional 1 cycle stays open, gated on the new residual row: it is the
  only lever in 4.1 that is both large (half the projection) and free in boiling flow,
  and at N=1024 the 30 fps stretch is one cycle away (4.97 -> ~3.0 ms/substep).
- confirmed in review: K=20 stays the default (`&k=40` documented as the conservative
  fallback), and the next captures are `fixed-k20`, `fixed-k40`, `cycles1` for the residual
  rows and `n1024-fixed` for the last t2 table row.

## a5 memory, closed from the allocation list

the plan's other unmeasured bar is gpu memory, and webgpu has no footprint query, so the
honest measurement is the allocation list itself: `Fluid.gpu.fields.memoryReport` walks
the same two lists `destroyPool` uses (27 textures, 8 buffers) and the new
`experiments/gpu-memory.js` prices them against a5 - 52.9 MB logical / 55.3 MB with 256 B
row padding at N=512 (bar 60, 7.8 % to spare), 209.7 / 214.6 at N=1024 (bar 200, 7.3 %
**over**). the page now prints the identical pair in its report (`gpu memory: ...`), so a
capture can confirm the model against what the browser believes. counted once and
deliberately left out of both numbers: the canvas backbuffer, driver block rounding, the
transient staging arrays, and the three profiler buffers.

what it says: five full-res rgba32float fields (mass x3, therm x2) are 80.3 MB of the
N=1024 total and cannot shrink; the other 128 MB is 22 textures of scratch and half
populated channels. plan 4.3's t7 candidate map, priced by `--whatif`, is 39.3 MB at
N=512 and 155.5 at N=1024 - so t7 alone clears a5 at both sizes, and a5 is now a
regression test rather than an aspiration: the N=512 assertion runs in `run-all.js`
(suite 18 of the quick profile, <1 s), which is what will notice if t5/t8 add a
full-res field without anything being dropped.
