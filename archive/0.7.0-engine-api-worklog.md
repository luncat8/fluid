## review of the previous task (0.6.0)

The last stage closed t8 (pass fusion stays off) and rejected t17 (vorticity
confinement on top of mac-cormack). What is left in 0.6.0 is device-bound: t7
half-float trials, t9 workgroup tuning, t10 the quality controller, t13 the
readback ring/display trial. None of those can be decided in this sandbox, and
the plan itself says an adoption needs a hardware row. So this stage takes the
next *code* step, 0.7.0, instead of writing an unmeasurable "trial".

Two things in the old loop were worth fixing while moving it, and both were
duplication hazards rather than performance:

- the app frame loop owned the substep policy, the accumulator, the paint flush
  and the in-flight gate. `experiments/performance.js` re-implemented the same
  loop to test it, and the CPU oracle and mock each had their own copy of the
  policy call. One owner is now `Fluid.engine.update()`; the lab page keeps only
  DOM work.
- the view mode had one writer per *entry point* (DOM row, keys) and a third path
  would have been the new API. `bindViewMode` keeps the DOM row the single writer
  and the engine setter delegates.

The mock device also existed once per harness. It now lives in
`experiments/mock-device.js` (command stream, canned readbacks, live allocation
counters) and is shared by gpu-mock.js and engine.js; "pool destroyed" became an
assertion instead of a comment.

### probe table

One storage buffer, `[count, pad x15, slot 0..31 * 16]` with a slot holding
`x, y, m, dr, dg, db, E, u, v, p, ..., active`. The kernel writes only the measured
values, so `moveProbe` is one `writeBuffer` and ids stay valid until `removeProbe`.
T and phase are derived on the CPU from (m, E) with `phaseInto` — the same closed
form the oracle and the WGSL `evalPhase` use, so the EOS is not re-implemented in a
third place. The readback shares the stats/buoy generation guard and the
single-map-in-flight rule; `sample()` returns false until the first readback and
after a reset or resize, and `out.age` is in frames.

The kernel uses `@workgroup_size(8)` and `dispatchWorkgroups(4)`:
`wgsl_reflect`'s interpreter silently executes only a prefix of a larger
workgroup (32 -> 3 invocations), which made the exec row look like a kernel bug.
8 threads per group run correctly there, so the kernel can be verified without a
device. On the GPU this is 4 tiny workgroups; the cost is noise.

## decisions

- `step(dt)` sets the fixed frame dt; the substep policy reads `cfg.frameDt`, so a
  caller cannot desync the policy from the step it gets. `update()` takes at most
  one fixed step per call and caps debt at two frame periods — catching up three
  steps in one callback only queues work already known to be late.
- `create` is the only promise. Everything else is synchronous and allocation-free
  on the frame path; `stats(out)` and `sample(id,out)` write into caller objects.
- `setGrid` clamps to [64, 1024] and marks the resize repaint as a submission in the
  pacing gate, so the next update waits for it like any other frame.
- `attachInput` installs pointer *and* key handlers through one listener list. A
  separate `bindKeys` is left as t8b; nothing in the demo needs it yet.
- the lab's browser-only query overrides stay in `main.js`: they are page features
  (`?mg=`, `?k=`, `?cycles=`), not engine configuration.

## review of this stage (what the tests found)

- the demo test was first written against a stub engine and still hid a real bug:
  the probe buffer is zeroed by a grid rebuild, so every probe silently stopped
  after `setGrid`. Booting the page on the real engine and the recording device
  caught it; `reset()` now re-uploads the table. A stub object cannot fail the way
  a real one does - the fixture has to be the engine, with only device acquisition
  faked.
- `examples/demo.js` calls `Fluid.engine.makeProbeSample` to preallocate its rows;
  the facade did not export it. A page is a good api test precisely because it
  calls the documented entry points instead of the ones the author remembered.
- the first ui-cadence drive advanced 16.7 ms per callback and every probe row
  stayed blank: the page refreshes at 2 Hz, so an 8-frame window never crossed the
  boundary. The harness now advances 100 ms per callback; real browsers do that on
  their own because the cadence is wall-clock, not frame-count.

## stage 2: t3 sources (2026-10-24)

`sim.addEmitter/moveEmitter/setEmitter/removeEmitter` + `emitterCount`, 8 stable slots.

- `src/core/emitters.js` owns the table and the ledger arithmetic. Slots are copied
  from the caller's spec at add time (a game may reuse one object) and pushed into
  one storage buffer; the header carries the live count and `energyFromT(1,TRef)`, so
  dye mass arrives at the temperature the wgsl EOS already calls ambient.
- Three kernels (`emitterMass`, `emitterTherm`, `emitterVel`) run at the top of the
  frame, before the substeps, with `dt = substep dt * substep count`. Each is a
  full-field copy into the next ping-pong parity plus the table's cell-local
  additions: a storage texture cannot be read and written in one pass, so the copy is
  unavoidable and the parity walk is the one `encodePaint` already uses. Only the
  fields the live kinds touch are staged (dye: mass+therm, heat/cold: therm,
  momentum: vel).
- kinds are `dye`, `heat`, `cold`, `momentum`. `drain` and `freeze` were dropped from
  the increment: how much they take depends on the cell's own mass/energy, and a
  request booked as a removal would show up as drift the moment a sink ran dry. They
  need a gpu-side removal counter (new plan task t3b) rather than an approximation.
- the ledger is updated in the same frame, before `rhoMean` is recomputed, so the
  injected mass is part of the mean density the substep solves against.

Validation:

- `node experiments/engine.js` - 75 checks (was 53): the table and stable ids, the
  add-time copy, the pass staging per kind, the ledger against an independent f64
  disc sum, `setGrid`/`reset` survival, the full-table refusal, an idle frame staging

- `node experiments/wgsl-exec.mjs` - 51 checks (was 45): the three kernels execute

## stage 4 - t4 moving colliders (2026-10-24)

Goal: a game object the sim moves through. two halves, and only one of them is a shader.

Built:

- `src/core/colliders.js`: an 8-slot body table (`circle` with `radius`, `box` with
  `hw`/`hh`, `vx`/`vy`, positions in cell units like probes) and an analytic
  `rasterize` into a per-cell owner byte `0 = free, id + 1 = body`, clipped to the
  interior `[1, texW-2] x [1, texH-2]`. the raster reports the bounds it wrote, so
  nothing sweeps the grid and the delta upload knows its rect without a readback.
  the circle test is `fround(dx*dx + dy*dy) <= fround(r*r)`, i.e. rim cells are
  inside, which is what makes a radius-4 body eight cells across.
- `src/gpu/shaders.js` `colliderVel` (8x8): one velocity copy plus a set-override over
  the patch rect, `p.a > 0.5` selecting a cell. it is a *set* of the body's rest/velocity,
  never an add, so re-running the pass cannot compound a body's own push.
- `src/gpu/fields.js`: `patchVel` (`rgba32float`, 128x128) in the pool, and
  `writePatchAt(device, texture, x, y, w, h, format, data)` for an origin-correct
  `writeTexture`. `patchVel` is in the allocation count, so `gpu-memory.js` stays exact.
- `src/gpu/solver.js`: `staticMask` (set by `setObstacles`/`paintObstacle`),
  `colliderOwner` and `colliderPrev` (the delta), `colliderRect`/`colliderPrevRect`,
  `flagsPatch`, `velPatch`, and `updateColliders()` at the top of `frame()` before the
  sources. the new mask is `max(staticMask, owner)`; the upload rect is the union of
  the previous and the current rect, as a patch when it fits 128 (one flags write plus
  one `patchVel` write) and as a full flags upload when it does not (a teleport, where
  the imprint would be meaningless anyway). the imprint and `encodePrimePhase` share
  one submit, so no substep runs against a half-updated boundary.
- `src/api/engine.js`: `setObstacles`, `paintObstacle`, `addCollider`, `moveCollider`,
  `setCollider`, `removeCollider`, `colliderCount`, each returning false / -1 when the
  solver is inactive, so a torn-down engine stays callable.
- `examples/demo.js` / `demo.html`: a Body button adds a box paddle and the frame loop
  bounces it across the tank with `moveCollider`, so a2 is visible as well as measured.

Decisions:

- the delta is computed on the cpu, not the gpu: the geometry is analytic and tiny, and
  a gpu reduction would need a readback (and a stalled queue) before the cpu could book
  anything. the plan's sketch said "gpu"; the cost model is the same one dispatch cheaper.
- `paintObstacle`'s kinds are `wall` and `erase`. the sketch's `solid` is a phase, and
  the phase field belongs to the EOS; accepting it here would have let the pointer and
  the caloric curve disagree. it is refused (and tested to be refused).
- releasing a cell restores `staticMask` rather than clearing it, so a body driving over
  a painted wall puts the wall back. without this, every moving body would erase the level.
- a body keeps the fluid that was already inside the cells it appears in: a wall is a
  boundary, not a drain. pushing that mass out would be a transport operation with its
  own conservation proof, and a2 only forbids creating mass (a teleport books nothing).
  **superseded in stage 5**: not pushing it out is what the object looked like it was
  doing - see "t4b the push" below. the core solver still treats a wall as a boundary;
  the push is an explicit pass the gpu path stages on the frames a body takes cells.
- colliders hold no params slot and no gpu buffer. a parked body costs nothing per frame;
  a moving body costs one flags write, one velocity patch write and one dispatch.

Validation:

- `node experiments/engine.js` - 103 checks (was 75): raster geometry and reported rect,

## next step

t6 serialize/deserialize, per the accepted order:

- one header (magic, version, N, frame, time, step policy) and the conserved fields, written
  into a caller-provided ArrayBuffer with a documented layout - no stringify, no allocation.
- a mismatched N, version or policy is refused with a clear message (no resampling).
- the readback goes through `copyTextureToBuffer` with the 256-byte row rule, which is the
  same padding the probe readback already handles; that makes the round-trip test the first
  real use of a full-field copy.
- the step policy fields (`substepsAuto`, `substepsFixed`, `substepMax`, `frameDt`) are stored
  because restoring the fields alone does not reproduce the trajectory.
- the round trip test belongs in `experiments/engine.js` (bytes, then 100 identical steps
  from both sides) with the field contents checked through the cpu oracle, since the mock's
  `writeTexture`/`copyTextureToBuffer` are recordings, not storage.


## stage 5 - t4b the push, and the textureLoad level (2026-10-24)

The reported symptom: after the shader error was fixed, the demo's body moved and the
mask updated, but nothing was pushed - "it looks like it freezes the material behind the
body while it moves over it". That is exactly what it did, and for a structural reason:

- a wall is a boundary the advection clamps at. the cells a body covers keep their dye
  and heat, and when the body moves on they are released unchanged. so the body slid
  over a picture of the water it had crossed, leaving a hole of stale dye behind it.
  the velocity imprint alone only moves the fluid it re-enters; it never moves what is
  under the body.

Also reviewed and fixed while in here: the four new kernels (`emitterMass`,
`emitterTherm`, `emitterVel`, `colliderVel`) read storage textures with a mip-level
argument (`textureLoad(t, coords, 0)`), which WGSL does not define for
`texture_storage_2d`. That is a validation error and, on a device that validates
strictly, the whole frame's submit could fail while the mock and the interpreter both
accepted it. the level argument is gone; a scan for the same pattern over every storage
texture read now reports none.

Built:

- `core/colliders.geometry(cfg, owner, prev, rect, geo, pitch)` marks, in the third
  channel of a patch-local 4-float stride, what a body took this frame: `> 0` a taken
  cell carrying its count of free neighbours, `-1` a cell that was already body, `0`
  free. a taken cell whose receivers are not all inside the rect keeps its contents, so
  a rect mistake (or a body sealed inside geometry) can never destroy substance.
- `core/colliders.displace(...)`: the cpu oracle, cell for cell the same walk: a taken
  cell is emptied (mass 0, energy 0, temperature back to `TRef`), each free neighbour
  adds `1/deg` of it. reads the pre-push contents through a scratch pair, so no order
  dependence.
- `shaders.colliderPushMass` / `shaders.colliderPushTherm` (8x8): the same walk as a
  gather over the patch, one full-grid pass per field, staged only on frames where the
  body took cells.
- `pool.patchGeo` (`rgba32float`, PATCH x PATCH) and `writePatchAt(..., pitch)` so the
  patch rows can be written at the GPU texture's stride.
- `passes.encodeColliderPush`, `groups.pushMass[m]` / `groups.pushTherm[t]`, and one
  submit per moving frame: push, imprint, phase prime - so no substep can see a half
  moved body.
- the imprint now skips cells that were solid last frame as well as this one: the fluid
  the body moved *into*, not the body.

Decisions:

- gather, not scatter. a scatter needs atomics or an ordering rule, and a cell taken
  twice would be counted twice. a gather reads the pre-push contents of the neighbours
  (each is written once), so the split is exact and order-free, and each cell costs four
  texture reads instead of a write conflict.
- equal split between free neighbours, computed from the mask. momentum is directionless
  here: a fluid cell has no idea which side the body came from without another patch, and
  the advection immediately afterwards supplies the direction anyway. the result is the
  visible behaviour (the dye bulges out around the body and the wake closes), not a
  physical pressure solve around the body - that is a much larger change.
- what is *not* moved: the latent-charge banks (`accum`) and the phase field (`sfield`).
  they are zero except during a phase change, they are not part of the conservation
  meters, and the phase pass right after the push recomputes flags from the fields.
- a teleport (a rect wider than the patch) still takes the full-upload path with no push:
  a jump is not a motion, and pushing a screen-wide rect out of a patch is undefined.
- cost: two extra full-grid dispatches, but only on frames where a body takes cells. a
  parked or teleporting body costs nothing; the demo's paddle moves about one cell per
  frame at 60 fps, so it pushes on nearly every frame and the passes join the moving-body
  row of the a1 budget.

Validation:

- `node experiments/engine.js` - 114 checks (was 103): the geometry codes and the split
  (one body cell with four free neighbours gives each a quarter of the dye and the heat,
  totals unchanged), a rect that misses the receivers and a body with no free neighbour
  both keep their contents, a cell the body already held does not push again, both push
  passes and the geometry patch are staged on a moving frame while a parked body stages
  nothing, and the visible half of a2 as a two-run contrast on the cpu oracle: the dye a
  body crosses stays 89% inside the swept cells without the push and 9% with it, the dye
  total identical either way, the mass still matching the ledger.
- `node experiments/wgsl-exec.mjs` - 64 checks (was 60): both push kernels execute
  against `core.colliders.displace` with zero difference, the dye total and the energy
  total are unchanged to 1e-10, taken cells read the reference temperature, and the
  ghost ring is copied, not sourced. the pre-existing storage-texture scan
  (every `textureLoad` on a `texture_storage_2d<..., read>` declaration takes exactly
  one coordinate argument) reports no remaining level arguments after the fix.
- `node experiments/gpu-mock.js` - all checks pass (t4b adds no pipeline to a parked
  frame); `node experiments/gpu-memory.js` - allocation accounting passes with
  `patchGeo` counted.
- `node experiments/run-all.js --quick` - 12/12, 6.4 s; `python3 run_tests.py` - 20/20
  suites, 971.6 s (`experiments/logs/2026-10-24-04-58-test-suite.log`).

Not validated: the device row. the push is the first collider pass whose cost per frame
depends on the body's speed, so a1's 60 fps at N=256 should be re-measured with the Body
button on. also unmeasured: whether an equal split looks right for a fast body (a body
moving more than its radius per frame steps over cells it never pushes) and whether the
emptied cell's edge reads as a seam at N=256.

## stage 6 - the missing push bind group (2026-10-24)

Symptom on the device, seen as soon as the Body button was pressed:

    No bind group set at group index 0 - while encoding ComputePassEncoder "collider"
    DispatchWorkgroups(33, 33, 1)

Root cause: `groups.pushMass[m]` was never created. the bind-group table had
`pushMass:[]`/`pushTherm:[]` in its initializer and the encoder read
`groups.pushMass[state.m]`, but the loop that should have filled it never did - the edit
that added it targeted a line with a trailing space and matched nothing, silently. so
`setBindGroup(0, undefined)` unbinds group 0, the first dispatch of the collider pass was
encoded with nothing bound, the device rejects the whole command buffer, the pass never
runs and the body neither pushes nor imprints - visible as "no error in the console until
you look, and the body does nothing".

Why the harnesses missed it: the recording mock's `setBindGroup` only pushed a number into
`bindings` and never cared, so `gpu-mock` and `engine` both saw the right `pipeOrder`
("colliderPushMass staged") while the real device dropped every dispatch. `wgsl-exec`
executes the shader directly and never builds a bind group, so it cannot see it either.

Fixes:

- the missing `groups.pushMass[m]` (params, mass source, mass destination, `patchGeo`),
  one per mass parity - the same src/dst pair `paintMass` uses, so `state.m` advances by
  one exactly like a paint frame.
- `experiments/mock-device.js` now tracks group 0 per compute pass and **throws** on a
  dispatch with nothing bound, naming the pipeline and the dispatch size:
  `mock: dispatch on pipeline "colliderPushMass" with no bind group at group 0 (x9y9z1)`.
  this is the check that makes the whole class of "the pass is staged but the device
  drops it" visible headlessly. reintroducing the bug now fails `engine.js` and
  `gpu-mock.js` immediately (verified by reverting the fix and watching it throw).
- `experiments/engine.js` asserts the parity coverage directly: `pushMass` has 3 groups
  with 4 entries each, `pushTherm` 2, `colliderVel` 2.
- `sim.solver.groups` is exposed next to `pool`/`state` so a harness can assert it.
- the demo does not drive the paddle while paused: a paused sim does not step, so moving
  the body only queues a jump for the resume frame (and a jump wider than a patch is a
  teleport, not a push).

Validation:

- `node experiments/engine.js` - 115 checks (was 114): the parity-coverage check, plus
  every existing collider check unchanged; the mock now fails any dispatch without a
  bind group, which every suite exercises.
- `node experiments/gpu-mock.js`, `experiments/gpu-memory.js`,
  `experiments/wgsl-exec.mjs` (64) - all pass.
- `node experiments/run-all.js --quick` - 12/12, 9.2 s; `python3 run_tests.py` - 20/20
  suites, 1290.4 s (`experiments/logs/2026-10-24-07-13-test-suite.log`).

Lesson for the worklog, since it cost two rounds of device feedback: a recording mock
that ignores bind state can prove a pass was *encoded* but never that it was *valid*. any
new pipeline should come with the group it needs created in the same edit, and the mock's
group-0 guard is the cheapest place to catch it.

## stage 6 - moving-body multigrid safety fallback (2026-10-24)

The CPU moving-paddle stress case isolated a failure that the shader-unit and mock suites
cannot catch: the conservative local mass/heat push creates abrupt density peaks, and the
variable-coefficient multigrid pressure solve can run away while the body moves. On a
64x64 still-fluid case using the demo's 5x9-cell paddle and 14.1 cells/s horizontal motion,
MG plus push plus the existing velocity imprint reached `maxM=38.8`, `maxVel=4.2e32`, and
`maxDiv=2.2e34` by frame 40, then became nonfinite at frame 43. The matching no-push CPU
