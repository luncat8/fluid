# 0.7.2 — one readback staging buffer, one map per frame

status: implemented and validated headlessly (mock device, allocation audit). device timing
row open (mapAsync latency on a real driver).
depends on: 0.7.0 t5/t6/t9 (probe, stats and phase-event readbacks)
record: archive/0.7.2-readback-worklog.md

## 1. goal

every asynchronous readback in the engine — the conservation stats, the buoy field sample,
the probe table, the phase-change batch — reaches the CPU through `mapAsync`. Before this
plan each channel owned its own `MAP_READ` buffer and its own poll loop, so a frame that
owed all four paid four map/unmap round trips, four mapped `ArrayBuffer`s and four
`Float32Array` views, plus four near-identical poll functions to keep in step.

the goal: one staging buffer, one map per frame, one poll path, one typed-array view per
map, and no loss of data or of the existing staleness guarantees.

## 2. what the spec allows, and what it does not

`GPUBuffer.getMappedRange()` returns an `ArrayBuffer`. Repeated calls within one map return
the same one (per offset/size), and `unmap()` **detaches** it. A view created over it is
therefore usable only until the next `unmap()`: caching `new Float32Array(getMappedRange())`
across frames does not remove the allocation, it produces a detached view that throws on
first read — and it appears to work on any mock device that hands back a stable buffer.

so the honest budget is one `ArrayBuffer` from the driver per map (unavoidable) and one
typed-array view over it (avoidable only by not reading the bytes at all). what is left to
save is the *number of maps*: that is where a frame's driver round trips come from.

consequences for the design:

- one map-read buffer with a slot per channel; a frame copies only the channels it owes,
  and one map reads whatever was copied.
- the mapped view is cached by `ArrayBuffer` identity, so a map that hands back several
  ranges (or a driver that reuses one buffer) costs one view and never reads a detached
  range.
- a copy is skipped while a map is in flight. the storage buffer keeps the newest values,
  so a skipped copy costs one frame of staleness, never a sample: the next copy picks up
  current data. this is the same one-in-flight rule the stats had.

## 3. layout

`src/gpu/fields.js` owns the layout (it owns every pool allocation):

	slot          floats  bytes   offset (256-byte aligned)
	stats           46     184        0
	buoy             6      24      256
	probes         528    2112      512
	phaseEvents    560    2240     2816
	                                total 5120

the sizes come from the modules that already own them (`core/stats`, `core/buoy`,
`core/probes`), so a channel cannot silently disagree with its ingest code. offsets are
multiples of 256, which satisfies `mapAsync`'s 8-byte and `copyBufferToBuffer`'s 4-byte
alignment rules with margin. the layout is grid independent — resizing swaps the buffer but
not the offsets.

## 4. wiring

frame (encode): `if(!readInFlight)` copy each due channel into its slot, record its bit in
`readMask`, and capture the expected conservation totals of that same frame. the capture
and the copy stay together, so stats can never be paired with another frame's ledger.

poll: take `readMask`, clear it, set the in-flight flag *before the first await*, map the
buffer, then ingest the channels whose bit is set and whose generation still matches (a
reset or a resize bumps the generation and drops the readback), unmap, clear the flag. the
phase-change callback still fires outside the map, after `unmap`.

## 5. validation

- `experiments/gpu-mock.js` (plumbing): the pool holds exactly one `MAP_READ` buffer and no
  per-channel read twins; the four slots are 256-aligned, ordered, disjoint and total to the
  buffer size; a frame owing all four channels encodes four copies at the four slot offsets
  and takes one map; a frame submitted while the map is open copies and maps nothing, and the
  following frame catches up with one map.
- `experiments/engine.js` (allocation): a step+poll cycle allocates exactly one typed array
  in `src/` per map — 40 maps, 40 `Float32Array` in `src/gpu/solver.js`, nothing else. the
  same measurement against the previous four-buffer code gives 120 maps and 120 allocations
  for the same 40 cycles.
- the mock device is now faithful about map semantics: a snapshot per `mapAsync`, one
  `ArrayBuffer` per (offset,size) per map, detached on `unmap`. a cached view would fail
  these tests instead of passing them.
- no numeric change is expected or checked here: this moves bytes into one buffer, it does
  not touch a shader, a kernel, an ingest rule or a conservation formula.

## 6. non-goals

no change to readback *cadence* (stats every `statsEvery` frames, probes `probeEvery`, the
buoy sample `buoySampleEvery`, phase events while a listener is registered), no change to
the staleness contract (`sample.age`), no attempt to remove the driver's per-map
`ArrayBuffer`, no folding of the save/load staging buffer or the GPU profiler resolve
buffers into this one (both are one-shot or opt-in, and both copy large textures).

if a future backend wants channels at independent cadences with no interaction at all, the
slot table is the place to add a ring of two staging buffers — one mapped while the other is
written — which is the only way to make a map and a submit overlap.
